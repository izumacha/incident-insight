## Security

### HTTPS / HSTS

本番では `UseHttpsRedirection` と `UseHsts` が有効化されます（HTTPS 終端はリバースプロキシ想定）。

### Cookie / antiforgery

- 認証クッキーや antiforgery は `SameSite=Strict`、本番では `Secure` を前提とします。

### レスポンスヘッダー

- `SecurityHeadersMiddleware`(`src/IncidentInsight.Web/Middleware/SecurityHeadersMiddleware.cs`)が
  全レスポンスに `X-Content-Type-Options: nosniff` / `X-Frame-Options: DENY` /
  `Referrer-Policy: strict-origin-when-cross-origin` を付与します(クリックジャッキング・
  MIME スニッフィング・Referer 経由の URL 漏洩対策)。
- 同ミドルウェアが**誰もキャッシュ指示を書かなかった応答**へ `Cache-Control: no-store` を
  付与します(PHI を含む画面・集計 JSON が共用端末のディスクキャッシュや共有キャッシュに
  残らないようにするため)。規則はこの 1 つだけで、応答の種類では振り分けません(将来 CSV・
  添付画像のエクスポートを足しても既定で保護される fail-closed)。すでに `Cache-Control` が
  書かれている応答(`HomeController.Error` の `[ResponseCache]`、`/health`、アンチフォージェリ、
  静的ファイル配信)は上書きしません。
- 静的アセット(`wwwroot` 配下)は `Program.cs` の `UseStaticFiles` が `OnPrepareResponse` で
  `Cache-Control: public,max-age=3600` を名乗ります。これが上の既定値を静的ファイルへ
  及ばせないための仕組みです(`lib/` 配下は版付き URL でないため、長期・`immutable` にはしません)。
  付与の根拠と実測(導入前は「フォームを持つ画面だけがアンチフォージェリ経由で偶然保護されて
  いた」)は `SecurityHeadersMiddleware` の docstring が正本です。
- **例外**: 同ミドルウェアより手前で応答が完結する経路が 2 つあり、そこには上記のヘッダー群が
  付きません。**どちらもこのアプリのデータを 1 文字も載せない**ため、PHI が漏れることは無いと
  判断しています(覆いたい場合の手当ては `Program.cs` の該当箇所のコメントが持ちます)。
  1. 本番の HTTP → HTTPS リダイレクト(`UseHttpsRedirection` が返す 307)。本文を持たず、
     307 は明示的な指示が無ければキャッシュされません。**ただし `Location` は要求元の
     `Host` をそのまま含みます**(`UseHttpsRedirection` は `Request.Host` から遷移先を
     組み立てるため)。つまりこの経路だけは「リクエスト由来の値を映し返さない」が
     成り立ちません —— そこを塞ぐのは次の項の `AllowedHosts` の絞り込み(issue #64)で、
     既定の `"*"` のままだと `Host: evil.example` が `Location: https://evil.example/...`
     として返り、前段の共有キャッシュがそれを保存して他の職員へ返しうる状態になります。
     **本番では必ず実ホスト名へ絞ってください。**
     なお `appsettings.json` に入っているのは既定の `"*"` で、**これは配備時の設定事項です**
     (実ホスト名をリポジトリ側で決められないため)。絞り忘れは機械的には検出できないので、
     `Program.cs` が起動時に警告ログ(`AllowedHosts is permissive in the {Environment} environment
     (current value: …)`)を出します。環境名と設定値そのものが載るので、`Staging` の設定ミスを
     本番の話と取り違えずに済みます(判定は `!IsDevelopment()` なので Production 以外でも通ります)。
     —— **配備後にこのログが出ていないことを確認してください。**
     **この警告は「なぜ絞れていないか」も名指しします。** 全許可になる経路は 3 つあり
     (①一覧に有効な項目が 1 件も無い ②ワイルドカードが混ざっている
     ③ホスト名として読めない項目がある)、直し方は同じでも**設定のどこを見ればよいかが違う**ためです。
     とくに ①③ では値にワイルドカードが 1 つも無いので、
     「`*` / `[::]` / `0.0.0.0` を消せ」とだけ案内すると**存在しないものを探させる**ことになります。
     **全許可になる綴りは `*` だけではありません**: `[::]`(IPv6 Any)と `0.0.0.0`(IPv4 Any)も
     同じで、**1 つでも混ざっていれば実ホスト名を併記しても許可リスト全体が無効**になります
     (`ASPNETCORE_URLS=http://0.0.0.0:8080` を写して `AllowedHosts` に書くと自然に起きます)。
     **判定はホスト名の正規化(IDNA / NFKC)の後に行われます** —— 全角数字の `０.０.０.０` や
     日本語 IME の読点で書いた `0。0。0。0` も `0.0.0.0` に正規化されるため同じく全許可です。
     **さらに「区切り文字だけ」の値(`;` ・ `;;`)も全許可になります** —— 空の項目を落とした結果
     1 件も残らないと、既定の `["*"]` へ落ちるためです。**テンプレート展開で生まれやすい形**なので
     注意してください(`AllowedHosts=${PRIMARY_HOST};${SECONDARY_HOST}` で両方が未定義だと `;` になります)。
     **一方、空白を挟むと逆に「一致しない項目」になります。** ホスト名の検査は項目を
     トリムしないため、前後に空白のある項目は原則どの `Host` とも一致しません
     (`" ; "` ・ `"  *  "` ・ `"   "` は実測でどれも 400)。
     **ただし「空白を足せば必ず死ぬ」わけではありません** —— 角括弧で書いた IPv6
     リテラルだけは、正規化が `]` より<b>うしろを捨てる</b>ので空白が消えます
     (実測: `"[::1] "` → `"[::1]"` で**一致する**、`"[::] "` → `"[::]"` で**全許可に戻る**)。
     そのため下記の 2 本目の警告は、生の綴りではなく**正規化したあとの綴り**を見て
     名指しします —— 生の綴りで判定していた頃は、200 で受けている `"[::1] "` を
     「消してよい」と案内しており、従うと IPv6 のクライアントが一斉に 400 になりました。
     **とくに危険なのは、一覧を書くときに自然に入る「区切りのうしろの空白」です**:
     ```
     AllowedHosts=incident.example.com; www.example.com   # ← 2 件目が死んでいる
     ```
     実測では 1 件目が 200・2 件目が **400** になります ——
     **サイト全体は生きたまま、特定のホスト名だけが静かに落ちる**ので、
     監視にもヘルスチェックにも出ません。しかも上の「全許可」の警告は
     (絞り込み自体は効いているので)正しく**出ません**。
     そこで `Program.cs` は**これ専用の 2 本目の警告**を出します
     (`AllowedHosts contains N entry/entries that can never match any Host header …`。
     死んでいる項目を `[ ]` で囲んで名指しし、**項目ごとにその理由を添えます** ——
     空白は目で見えないため囲み、理由が 1 つではないため項目ごとに添えます)。

     **同じ「静かに落ちる」形がもう 1 つあります: ポートを含む項目です。**
     突き合わせのとき、リクエスト側の `Host` は**ポートを落としてから**比べられる一方、
     許可リストの項目は**そのまま**比べられます。したがって
     ```
     AllowedHosts=incident.example.com;www.example.com:8080   # ← 2 件目が死んでいる
     ```
     の 2 件目は、`Host: www.example.com` でも `Host: www.example.com:8080` でも
     一致せず**毎リクエスト 400** になります（どちらも実測）。
     `ASPNETCORE_URLS=http://0.0.0.0:8080` からホスト名を写すとポートごと持ってくるのは
     `0.0.0.0` を写してしまうのと同じくらい自然な形です。
     **`AllowedHosts` にポート番号は書かないでください**（ホスト名だけを並べます）。
     なお `[::1]` のような角括弧の IPv6 リテラルはコロンを含みますが**ポートではない**ので、
     この警告の対象にはなりません（実測で正しく一致します）。
     この警告は**名指しした項目 1 件の事実だけ**を述べ、一覧全体の症状は名乗りません ——
     残りの項目しだいで、すべて 200（ワイルドカードが混ざっている）・その 1 件だけ 400
     （生きた項目と混在）・すべて 400（生きた項目が 1 つも無い）・毎リクエスト例外
     （正規化できない綴りが含まれる）と変わるためです。**「生きた項目が 1 つも無い＝すべて 400」
     とは限りません** —— 同じ一覧に正規化できない綴りが混ざっていると、400 ではなく
     フレームワークが例外を投げます（500 相当）。たとえば `AllowedHosts=0.0<TAB>.0.0; `
     は、名指しされるのは末尾の `" "` だけですが、実際の症状は 400 ではなく例外です
     （`0.0<TAB>.0.0` 自体は正規化できないため名指しされません。下記のとおり、
     正規化に失敗する綴りは 1 本目の警告が専用の文面で扱います）。
     **削除してよいかは「死んだ項目を消したあとに残る一覧」で決まり、警告の文面が
     そのつど正しい直し方を名指しします。** 判断は 3 通りあります:
     1. **消してよい**（残るのが実ホスト名だけ）。
        `AllowedHosts=incident.example.com; ${SECONDARY}` で `SECONDARY` が未定義のときは、
        書き換える先の実ホスト名が無いので末尾の `; ` を削除するのが唯一の直し方です。
     2. **消してはいけない**（消すと残る一覧がどの `Host` でも受け付ける状態になる）。
        経路は 2 つあり、**「生きた項目が残るかどうか」では判別できません** ——
        項目が 0 件になって既定の `["*"]` へ落ちる形（`"   "` ・ `" ; "`）と、
        **残った項目自体がワイルドカードの形**（`"*; "` ・
        `"incident.example.com;0.0.0.0; "`。後者は `ASPNETCORE_URLS` を写すと自然に生まれます）。
        直し方は**実ホスト名だけが残る状態にすること**で、名指しされた項目の書き換えに加えて
        **ワイルドカードの項目（`*` / `[::]` / `0.0.0.0`）も消す**必要があります。
     3. **判断できない**（残る項目にホスト名として読めない綴りがある）。
        この場合の結果は**項目の並び順で変わります** —— 実測では
        `"0.0<TAB>.0.0;0.0.0.0"` は例外（どの `Host` も受け付けない）、
        並びを入れ替えた `"0.0.0.0;0.0<TAB>.0.0"` は 200（どの `Host` も受け付ける）でした。
        一覧全体を作り直し、実ホスト名だけを残してください。

     なお、**2 本目の警告が検出できるのは「正規化後に前後の空白が残る項目」と
     「ポートを含む項目」の 2 つだけです** —— `0.0<TAB>.0.0` のように
     項目の途中へ制御文字が紛れた形（正規化そのものに失敗する綴り）は名指しされず、1 本目だけが出ます
     （そのとき 1 本目は上記③の文面になり、「読めない項目がある／値にワイルドカードは
     無いかもしれない／症状は全拒否ではなく毎リクエストの例外」と述べます）。
     複数の項目が壊れていても、名指しされるのはこの 2 つに当たるものだけです。
     **括弧の内側へ入った空白も名指しできません** —— 素の IPv6 を書くと `HostString` が
     括弧を補うため、`"::1 "` は `"[::1 ]"` となって空白が内側へ移ります
     (実際には一致しないので**見逃す側**の誤りです。生きている項目を「消してよい」と
     案内する逆向きの誤りより安全なので、この形を選んでいます)。
     **警告の有無にかかわらず、一覧の項目は 1 つずつ目視で確認してください。**
     一覧は空白もポート番号も入れずに `a.example;b.example` と書きます。
     **配備後は 2 本とも出ていないことを確認してください。**
     判定の正本は `Models/Validation/AllowedHostsPolicy`(既定設定をそのまま写した理由と
     境界の実測値はその docstring にあります)、実際の挙動は
     `HostFilteringShortCircuitTests` が固定しています。
  2. ホスト名の絞り込み(`AllowedHosts` を実ホスト名へ絞ったとき。issue #64。
     既定の `"*"` のままなら短絡しません)。一致しない `Host` ヘッダーには 400 が返ります。
     これは汎用ホストが `IStartupFilter` として登録するミドルウェアなので、`Program.cs` の
     並べ替えでは**手前に出られません**。実測では `Cache-Control` は付きませんが、
     **本文は空ではなく**フレームワークの定型ページ(`Bad Request - Invalid Hostname`)が
     返ります。安全なのは「空だから」ではなく「定型文で、要求元のホスト名も業務データも
     含まないから」で、その 2 点は `HostFilteringShortCircuitTests` が固定しています
     (映し返しがあると、キャッシュ抑止の効かない応答に攻撃者の入力が載ることになります)。
- Content-Security-Policy は未実装です。nonce なしのインライン `<script>`(ダッシュボードの
  JSON 埋め込み・テーマ復元スクリプト等)を複数箇所で使用しているため、`'unsafe-inline'` なしで
  安全に導入するには別途リファクタが必要です。

### Secrets

- 本番のパスワード/接続文字列は `appsettings.json` に書かず、環境変数や Secret Manager を使ってください。
